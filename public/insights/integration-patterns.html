Integration Patterns for Legacy Systems

Common patterns and anti-patterns when connecting modern applications to legacy infrastructure.

Most organizations operate some systems that would, ideally, be replaced—but cannot be, for reasons of cost, risk, or organizational capacity. These legacy systems often contain critical data and business logic accumulated over decades. Modern integration efforts must work with legacy infrastructure rather than around it.

This article describes patterns we have found effective when integrating modern applications with legacy systems, and anti-patterns that consistently cause problems.

Effective Patterns

Facade Layer

The most reliable legacy integration pattern involves building a facade layer that presents a clean interface to modern systems while handling the complexity of legacy communication internally.

The facade accepts requests in a standard format, translates them to whatever protocol the legacy system requires, executes the operation, and translates responses back to the standard format. All legacy-specific logic is contained within the facade.

Benefits: Modern systems never interact directly with legacy protocols. Legacy complexity is isolated. The facade can be extended to handle multiple legacy systems with a single interface.

Costs: Additional infrastructure to build and maintain. Latency added by translation layer. Facade becomes a critical dependency.

Change Data Capture

When real-time integration is required but legacy systems lack adequate APIs, change data capture (CDC) provides an alternative. CDC monitors the legacy system's data store directly, capturing changes as they occur and publishing them to downstream systems.

This pattern requires access to the legacy database and understanding of its schema—but does not require changes to the legacy application itself.

Benefits: No modifications to legacy systems. Near real-time data availability. Complete change history captured.

Costs: Tight coupling to legacy database schema. Changes to legacy schema require CDC updates. Potential performance impact on legacy database.

Batch Extract and Sync

For use cases that do not require real-time data, batch extraction remains a reliable pattern. Scheduled processes extract data from legacy systems, transform it to required formats, and load it to modern data stores.

This pattern is well-understood and can be implemented with minimal risk to legacy systems.

Benefits: Simple to implement. Minimal impact on legacy systems. Well-established tooling available.

Costs: Data is not real-time. Batch failures can cause significant data gaps. Reconciliation required between systems.

Anti-Patterns to Avoid

Direct Database Access from Multiple Systems

Allowing multiple modern systems to query legacy databases directly creates a maintenance problem that compounds over time. Each system develops its own understanding of the legacy schema, its own query patterns, and its own assumptions about data meaning.

When the legacy system changes—and it will—every consuming system must be updated. When performance issues arise, there is no single point of control. When data interpretation questions emerge, there is no authoritative source.

Prefer a single integration layer that mediates all access to legacy data.

Bidirectional Sync Without Conflict Resolution

Attempts to maintain identical data in both legacy and modern systems, with changes flowing in both directions, consistently cause problems. Without explicit conflict resolution, concurrent changes create data inconsistencies that are difficult to detect and harder to resolve.

If bidirectional flow is required, establish clear rules for conflict resolution before implementation—and build infrastructure to detect and handle conflicts when they occur.

Optimistic Timeline Estimates

Legacy integration projects routinely exceed initial estimates. Legacy systems contain undocumented behaviors, edge cases that only manifest under specific conditions, and dependencies that are not apparent until integration begins.

Plan for discovery. Budget time for understanding legacy behavior before committing to integration approaches. Expect to revise plans as understanding develops.

Planning Considerations

Before beginning legacy integration work:

Understand the legacy system's role. What business functions depend on it? What data does it contain that is not available elsewhere? What would happen if it failed?

Document current integration points. What systems already connect to the legacy system? How? What assumptions do they make?

Assess available interfaces. Does the legacy system offer APIs, file exports, database access, or other integration options? What are the constraints of each?

Identify ownership. Who maintains the legacy system? Who can authorize changes? Who understands its behavior?

Define success criteria. What specific capabilities must the integration provide? What latency is acceptable? What accuracy is required?

Legacy integration is often the most constrained part of a modernization effort. Time spent understanding constraints before beginning implementation is rarely wasted.
